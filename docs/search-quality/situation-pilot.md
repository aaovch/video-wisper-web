# Пилот предметных карточек и единый протокол

История первого пакета [плана](plan.md). Описанные ниже 24 карточки и результаты сохранены без замены. Текущее состояние — [расширенный пилот на 113 главах](expanded-pilot.md): он принят для обычной локальной сборки. Основной скилл пока не изменён.

## Корпус и разделение данных

Восемь записей: `sablya-a-3`, `sablya-a-5`, `soedinenie-dlinnyi-mech-lager-noname-1`, `longsword-a`, `mech-i-bakler-mikrotsikl-1-osnovy`, `hema-prednamerennye-ekspromtnye`, `kontseptsiya-monitoringa`, `2026-07-06-19-26-42`.

По три выбранные главы каждой записи: 24 карточки. Это частичное покрытие, не обработка всех глав. Проверочные вопросы затрагивают также главы без карточек, чтобы видеть влияние конкуренции.

Карточки написаны и материализованы раньше вопросов. Это уточнение порядка работ позволяет не передавать генератору тестовые формулировки. Затем вопросы зафиксированы до первого измерения ранжирования. Автор один; разделение проходов не является независимой человеческой оценкой. Набор развития и отложенный набор находятся в одном реестре, а runner по умолчанию выполняет только development. Сами вопросы автору известны, поэтому защищаемся от прямой подгонки процедурой, а не заявляем слепой эксперимент.

Реестр: `scripts/search-enrichment/pilot-registry.json`, контрольная сумма рядом. 60 семейств: 40 одиночных задач, 8 задач с двумя разными записями, 12 запросов о личных фактах, не предоставленных пользователем. Разделение — 40 development / 20 holdout. Варианты с опечаткой в этом первом новом прогоне ещё не добавлены; прежние фехтовальные наборы с опечатками остаются отдельными регрессиями.

Для личных фактов сохранена причина недостаточности информации и связанная глава с grade=1. Возвращённый связанный материал может быть полезен; nonempty не объявляется ложным фактическим ответом. Общий алгоритм оценки отвечаемости ещё не реализован. Для grade=3 проверяются известные поддерживающие главы, остальные результаты остаются неразмеченными, а не автоматически неверными.

## Контракт карточки

Sidecar `src/lib/data/search-cards/<slug>.json` содержит version=1, reportSlug, promptVersion, generator, dictionarySha256, cards. Каждая карточка содержит chapterIndex, sourceHash, termIds и необязательные поля situation/problem/action/conditions/limitations. Каждое поле — `{text,evidence}`; evidence является точной цитатой из заголовка, summary или тезисов соответствующей главы. Поля не заполняются ради полноты. Термины должны существовать в каноне и подтверждаться контекстом.

Валидатор проверяет форму, происхождение и цитаты, но не доказывает правильность причинной связи. Смысловая проверка пилота выполнена чтением выбранных глав при написании карточек. Полные записи этим проходом не переаннотировались.

При импорте сначала полная валидация, затем запись временного файла и замена целевого файла. Сбой валидации не меняет действующий sidecar. Изменение главы или версии словаря отвергает устаревшие карточки при их использовании. Отсутствующий sidecar допустим. Старый enrichment v1 и новые карточки хранятся раздельно; автоматической миграции нет.

`node scripts/search-enrichment/cards-cli.mjs status <slug>` возвращает missing/partial/complete и номера непокрытых глав. `--require-complete` делает неполноту ошибкой; на пилоте этот флаг закономерно не проходит: покрыто 24 из 113 глав, а не все восемь записей целиком.

```powershell
node scripts/search-enrichment/cards-cli.mjs prepare <slug> --dry-run
node scripts/search-enrichment/cards-cli.mjs prepare <slug>
node scripts/search-enrichment/cards-cli.mjs import <slug> <candidate.json> --dry-run
node scripts/search-enrichment/cards-cli.mjs import <slug> <candidate.json>
```

Команды возвращают JSON ok/error/artifacts; import также сообщает покрытие глав. Материализация подготовленного пилота: `node scripts/search-enrichment/materialize-pilot-cards.mjs --dry-run`, затем без флага. Это воспроизведение авторской спецификации с точными ссылками на тезисы, не алгоритм генерации новых карточек.

## Словарные правила

`src/lib/data/search-term-rules.json` содержит происхождение, canonical ID, примеры translation/spelling/asr, отрицательные примеры, блокировку «окно» и явные неэквивалентные понятия. Runtime берёт список включённых пресетов из этого файла. Пять уже принятых групп сохраняют прежнее поведение; новые широкие синонимы не включены. Поэтому отдельный «новый словарь» не заявляется отличающимся вариантом поиска в этом прогоне.

## Сравнение

```powershell
node scripts/search-enrichment/pilot-run.mjs
```

Runner проверяет source/registry provenance, собирает baseline и карточки, вызывает настоящий searchScoped на одинаковом реестре и восстанавливает обычный индекс в finally. Карточки добавляются только в field_context; исходные сниппеты и точные совпадения не заменяются. В первой ревизии `SEARCH_CARDS=1` включал их при сборке, по умолчанию они были выключены; текущее значение изменено после расширенного пилота. В прошлых экспериментах wholeChapters/indexedCoverage остаются выключены.

Одиночные вопросы проверяются в записи, всех её публичных коллекциях и архиве. Задачи по двум источникам — в архиве; личные вопросы — в записи. Дедупликация глав соответствует интерфейсу, принадлежность области проверяется автоматически. Отчёт включает Hit@5/MRR, известное покрытие нескольких источников, индивидуальные потери, размер gzip core и Node timings. Это не замер мобильного браузера и не полноценная Precision@5 без полной разметки.

Результаты development: `docs/search-quality/pilot-development.json`; полные выдачи — `.codex/search-pilot/development-*.json`. Пороговые критерии взяты из плана: +10 п.п. Hit@5 коллекций, отсутствие потерь, не более +20% gzip core и +10% p95 на том же устройстве. Если development не проходит критерии, holdout не раскрывается и карточки не включаются по умолчанию.

Для однократного финального прогона выбранной конфигурации: установить `PILOT_SPLIT=holdout` и выполнить runner. После него набор перестаёт считаться нераскрытым. Перед дальнейшей настройкой нужен новый отложенный набор.

## Полученные результаты и решение

Конфигурация карточек и веса не менялись между прогонами. Ни один результат ниже не заменяет предыдущий.

| Проверка | Запись Hit@5 | Коллекции Hit@5 | Архив Hit@5 | Индивидуальные потери |
|---|---|---|---|---|
| Development, 40 вопросов / 97 сценариев | 18 → 21 из 24 | 15 → 26 из 33 | 7 → 11 из 24 | 0 |
| Исходный holdout, 20 вопросов / 58 сценариев | 14 → 14 из 16 | 17 → 17 из 22 | 9 → 9 из 16 | 0 |
| Дополнительные 16 вопросов / 54 сценария | 15 → 15 из 16 | 15 → 16 из 22 | 7 → 9 из 16 | 0 |

Первый split оказался несбалансированным по покрытию: development сосредоточен на карточках, holdout — преимущественно на необработанных главах. Поэтому +33,3 п.п. на development нельзя переносить на общий поиск. Это ограничение дизайна, а не повод скрыть нулевой результат holdout.

Дополнительный набор (`pilot-confirmation.json`) подготовлен **после** этого наблюдения, но до собственного прогона: по одному вопросу на обработанную и необработанную главу каждой записи. Это 16 новых формулировок, не новые независимые темы. Он не заменяет исходные 60 вопросов. Хеш карточек зафиксирован и проверяется evaluator; карточки и веса не менялись. В коллекциях прирост +4,5 п.п., ниже целевых +10 п.п.

Решение первого пилота: **SEARCH_CARDS оставался выключенным по умолчанию.** Порог принятия не ослабляется. Основной скилл и массовая обработка архива пока не меняются. Размер gzip core вырос с 1 659 312 до 1 661 127 байт (примерно 0,11%); ресурсные пороги пройдены в Node-замере, но это не проверка мобильного UX.

На старом фехтовальном наборе (228 сценариев) карточки не потеряли прежние попадания Hit@5; отрицательные запросы сохранили пустую выдачу. Задачи с двумя источниками улучшились на development, но остаются сложными. Вопросы о личных фактах по-прежнему возвращают связанные материалы: полноценной оценки достаточности ответа нет.

Сводки: [development](pilot-development.json), [исходный holdout](pilot-holdout.json), [дополнительная проверка](pilot-confirmation-holdout.json). После этих прогонов оба контрольных набора раскрыты.

Для повторения дополнительной проверки:

```powershell
$env:PILOT_SPLIT='holdout'
$env:PILOT_REGISTRY='scripts/search-enrichment/pilot-confirmation.json'
node scripts/search-enrichment/pilot-run.mjs
Remove-Item Env:PILOT_SPLIT
Remove-Item Env:PILOT_REGISTRY
```

Следующая итерация: расширить карточки на большее число глав выбранных записей; заранее балансировать новый контроль по оружию, типу задачи и покрытию; дополнить варианты опечатками. Генератору не передавать раскрытые вопросы. Только после отдельного подтверждения эффекта переходить к обязательному workflow и скиллу.

Технический итог: 55 обычных тестов прошли, четыре исследовательских теста штатно пропущены в общей команде; pilot и fencing выполнены отдельно. Проверка типов — 0 ошибок/предупреждений, production build успешен. Финальный manifest подтверждает `situationCards.enabled=false`, `wholeChapters=false`, `indexedCoverage=false`. Скилл и публикация не изменены.

## Что ещё требуется до основного скилла

Принять конфигурацию по измерениям; дополнить вопросы вариантами опечаток; проверить прежние регрессии и поведение частичной поддержки; затем добавить локальный поисковый gate новой записи и пройти workflow на двух новых и одной изменённой записи. Массовое покрытие коллекций и изменение основного скилла до этих проверок не выполняются.
