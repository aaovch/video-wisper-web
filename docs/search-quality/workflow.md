# Подготовка и проверка поисковых карточек

Реальные пользовательские запросы закреплены в `scripts/search-enrichment/user-queries.test.ts`:
«подготовка атаки через длинное острие», «силовой батман», «перенос уколом».
Для позиции «длинное острие» runtime требует цельное сочетание в названии или тексте
результата с учётом словоформ и е/ё. Совпадение отдельных слов по разным частям отчёта
не должно вытеснять главы об этой позиции. Это узкое правило для подтверждённого термина,
а не автоматическое объединение любых соседних слов в обязательную фразу.

Карточки готовятся после окончательной правки смысловых глав. Источник истины — отчёт; цитаты и таймкоды не меняются ради поиска. Обычная сборка использует готовые карточки без вызова модели. Схема описана в [пилоте](situation-pilot.md), принятые результаты — в [расширенном пилоте](expanded-pilot.md).

## Команды из корня сайта

При создании фехтовального отчёта в Python CLI использовать `build-report --require-search-cards`
в dry-run и записи. Artifact `search_preparation` содержит дальнейшие команды и рабочую папку.
Поле `search_cards_required: true` сохраняется при пересборке. Для такого отчёта **обычный** аудит
и обычная сборка индекса отклоняют `missing` и `partial`; строгий флаг QA больше не единственная защита.
Отсутствие необязательных карточек в старом архиве по-прежнему допустимо.

```powershell
# Read-only аудит: полный JSON либо компактная сводка.
node scripts/search-enrichment/audit.mjs --all --summary
node scripts/search-enrichment/audit.mjs <slug>
node scripts/search-enrichment/audit.mjs <slug> --require-complete

# Подготовка источников, затем чтение пакета агентом.
node scripts/search-enrichment/cards-cli.mjs prepare <slug> --dry-run
node scripts/search-enrichment/cards-cli.mjs prepare <slug>

# Импорт подготовленного кандидата после смысловой проверки.
node scripts/search-enrichment/cards-cli.mjs import <slug> <candidate.json> --dry-run
node scripts/search-enrichment/cards-cli.mjs import <slug> <candidate.json>

# Полный QA с обязательным покрытием выбранной записи.
node scripts/qa-report.mjs <slug> --require-search-cards
```

Проверять exit code и JSON `ok`. Пути брать из `artifacts[]`, причины — из `error` и `reports[]`. `prepare --dry-run` и `import --dry-run` не записывают файлы. Кандидат проходит валидацию до замены существующего sidecar. Неудачный импорт сохраняет старый файл.

Для QA с флагом использовать прямой вызов Node: в текущем Windows-окружении вызов через `npm run qa-report -- <slug> --require-search-cards` потерял дополнительный флаг. Обычный `npm run qa-report -- <slug>` по-прежнему работает и включает общий аудит карточек.

## Работа агента

Проверенные связи источников: [контракт](source-links.md), [расширение v2](source-links-v2.md).
Сохранять пороги каждого сценария в `source-links-regressions.json`; прямую выдачу и доступ
через ссылки проверять с обычным внутренним лимитом. Для разбора пропусков использовать
[диагностику областей и глубины](source-links-diagnostics.md): внешний `limit=120` не снимает
внутренний лимит смысловой выдачи. Источники вне области учитывать отдельно. Доступ
через дополнительный переход измерять отдельно. Связи показываются
отдельными ссылками у найденной главы, не повышают её поисковый балл и не означают готовый ответ.
После изменения связанной главы пересмотреть обе стороны связи и выполнить
`node scripts/search-enrichment/source-links.mjs`; обычная сборка также отклоняет устаревшие связи.

Связанная выдача теперь предпочитает конкретные главы общим обзорам; точные совпадения сохраняют
порядок. [Парная проверка и ограничения](passage-order.md). При поисковой подготовке сохранять
`passage-quality.test.ts`, который требует оба источника для принятого составного вопроса.
Автоматический контекст соседних глав [отклонён](neighbor-context.md):
`SEARCH_NEIGHBOR_CONTEXT` в обычном workflow не задавать. Положительные случаи кандидата не заменяют
регрессии предыдущих принятых этапов.

### Буквальный контекст для базового покрытия

Принят второй режим `extractive-context`: он переносит точные названия записи и главы в контекст
поиска, не создавая новых утверждений. [Проверка на всём фехтовальном каталоге](all-fencing.md).
Для новой записи без ситуационных карточек можно начать с него; для проблемных вопросов сохраняется
описанный ниже workflow смысловых переформулировок. Не заменять проверенные ситуационные карточки
механическим контекстом только ради удобства. В итогах различать два режима: `complete` означает
валидное покрытие, а не индивидуальную LLM-переформулировку или доказанную релевантность каждого вопроса.

```powershell
node scripts/search-enrichment/cards-cli.mjs prepare-context <slug> --dry-run
node scripts/search-enrichment/cards-cli.mjs prepare-context <slug>
# Путь кандидата взять из artifacts[0].path; команда prepare-context не меняет рабочий sidecar.
node scripts/search-enrichment/cards-cli.mjs import <slug> <candidate.json> --dry-run
node scripts/search-enrichment/cards-cli.mjs import <slug> <candidate.json>
node scripts/qa-report.mjs <slug> --require-search-cards
```

Для восстановления `extractive-context` заново сформировать кандидат из изменённого отчёта:
никакой ручной замены хешей. Аудит выдаёт соответствующий `prepareArgs`. Названия и цитаты проверяются
буквально; техника не выводится из названия. Для ситуационных карточек нужен смысловой пересмотр.
Текущее покрытие всех коллекций: `node scripts/search-enrichment/coverage.mjs --save`.

### Ситуационные переформулировки

1. Прочитать пакет `prepare`: главы, хеши и подсказки канонического словаря. Не передавать генератору проверочные запросы.
2. Подготовить только подтверждённые поля situation/problem/action/conditions/limitations с точными цитатами. Словарь помогает распознать термин, но не доказывает наличие техники. Не заполнять отсутствующую причинную связь или упражнение ради схемы.
3. Проверить смысл, отрицания, условия и область применимости отдельно от машинной проверки. Точная цитата сама по себе не доказывает корректность переформулировки.
4. Выполнить import с dry-run и затем запись. Проверить аудит с `--require-complete`, если заявлена полная поисковая подготовка записи.
5. Выполнить строгий QA и проверить в браузере поиск внутри записи и коллекции, исходную цитату и переход к главе/времени.

Дополнения v1 в `search-enrichment/` остаются совместимыми. Новый workflow карточек не требует параллельно генерировать второй набор v1. Если существующий v1 sidecar устарел после изменения главы, обновить его через его собственный CLI; индекс продолжает проверять его происхождение.

## Статусы и восстановление

| Статус | Значение | Поведение QA |
|---|---|---|
| `complete` | Все главы покрыты, данные валидны | Пропускает |
| `partial` | Валидна только часть глав | Отклоняет при `search_cards_required` или строгом режиме |
| `missing` | Sidecar отсутствует | Отклоняет при `search_cards_required` или строгом режиме |
| `stale` | Изменилась глава или версия словаря | Отклоняет |
| `invalid` | Повреждён JSON, нарушена схема/цитата либо отсутствует отчёт для sidecar | Отклоняет |

Аудит всех записей также находит sidecar без соответствующего отчёта. Для неполных и устаревших данных возвращаются `recovery.chapterIndices`, `prepareArgs` и инструкция восстановления. При изменении словаря нужен пересмотр терминов всех затронутых карточек; при изменении одной главы — этой главы. Сохранять проверенные неизменившиеся карточки. **Нельзя чинить устаревание одной заменой хеша без чтения нового источника.** При повреждённом или отсутствующем отчёте сначала исправить источник/привязку, а не запускать генерацию вслепую.

Полный QA сначала проверяет все sidecar, поскольку сборка индекса глобальная. Затем, если указан `--require-search-cards`, требует полное покрытие выбранной записи. Отсутствие необязательных карточек в остальном архиве не требует доступности модели и не блокирует сборку.

## Проверенная граница

Актуальная интеграционная проверка: `node scripts/search-enrichment/lifecycle.mjs` из папки сайта.
Она запускает настоящий Python CLI в новой временной рабочей папке на двух сохранённых реальных
источниках (22 и 23 главы), затем Node prepare/import, повторный build, изменение одной главы,
отказ старого импорта и пересмотренное восстановление. Результат: [lifecycle.json](lifecycle.json).
Это проверка ветки **создания новых отчётов из кэша**, без повторного скачивания/Whisper и без правки
боевых исходников. Она заменяет прежний тест, который только копировал готовые отчёты; новый
транскрибационный intake не проверялся и не требуется для изменения поискового контракта.

Ниже сохранена историческая граница предыдущего этапа (до внедрения требования в CLI).

В изолированной временной копии двух реальных отчётов проверены создание двух новых sidecar через prepare/import, отсутствие записи при dry-run, обнаружение изменения одной главы, отказ импорта старого кандидата, восстановление пересмотренным кандидатом и сохранение остальных карточек. Дополнительно проверены частичное покрытие, смена словаря, повреждённый JSON и sidecar без отчёта.

Это технический тест workflow на существующих материалах, **не два новых видео и не полная проверка их intake**. На реальной записи `sablya-a-3` выполнен прямой строгий QA. Основной скилл и pipeline/quality rules теперь включают эту процедуру. Полная приёмка шага 7 по-прежнему требует подтверждения на двух новых видео и одной изменённой записи в обычном процессе. Проверка нового пакета на двух существующих записях и её ограничения: [austrian-batch.md](austrian-batch.md).

Проверка реализации: строгий QA завершён успешно, 58 тестов прошли, пять исследовательских тестов штатно пропущены в общем наборе; диагностика кандидатов выполнена отдельно. Проверка типов — 0 ошибок и предупреждений, production build успешен. В существующей записи осталось предупреждение SOURCE_STEM_LEGACY, не относящееся к поисковым карточкам.

## При добавлении новых карточек

Проверяй общий QA, даже если менялась одна запись: статистика BM25 общая для индекса.
При эксперименте сохраняй хеши источников, конфигурации и результатов; параллельные правки
корпуса требуют нового сравнения на одной версии данных. Нулевой прирост не называй успехом
ранжирования. Не подгоняй карточки под раскрытые проверочные вопросы.

Видимую выдачу считай после группировки одинаковых назначений. Упражнения с одним названием
и разным временем — разные результаты; повторные попадания в одну главу — одно. Не смешивай
эту метрику с историческим рангом сырых попаданий.
