# Глубокая проверка поиска — 6 сентября 2026

**Главный результат:** текущий движок заметно теряет качество на новых вопросах. На отложенных 24 вопросах нужная глава появляется в первых трёх результатах всего архива в **12/24** случаях. В локальном эксперименте E5 даёт **19/24**, а E5 + лексический поиск + повторное ранжирование — **21/24**. При этом есть регрессии, тяжёлые переформулировки и проблема запросов без ответа. Переносить нейросетевой вариант в сайт без дополнительной проверки пока преждевременно.

Работа добавляет лабораторию и тесты. Новые модели и экспериментальные алгоритмы не включены в браузерный бандл; текущее поведение сайта в этой итерации не изменено. Предыдущие локальные исправления поиска сохранены. Публикации не было.

## Что проверено

- Полный рабочий индекс: **158 записей, 24 860 документов**, два шарда MiniSearch. В публичной области доступны **150 записей**; закрытые коллекции не разблокировались.
- Нейросетевой и альтернативные лексические индексы: **2 572 главы** этих 150 записей. Один документ = название главы + summary + тезисы; contextual-варианты дополнительно используют название записи.
- **48 исходных вопросов по 14 записям**: 24 старых development-вопроса и 24 новых holdout-вопроса по восьми другим записям.
- Ещё 48 вариантов с удалением одной буквы в длинном слове, 12 ручных переформулировок и 6 запросов без предполагаемого ответа. Итого **114 формулировок, 330 сценариев областей, восемь вариантов поиска, 2 640 сравнительных прогонов**.
- Для current используются настоящий `searchScoped`, настоящие шарды, лимиты 30 для архива и 120 для отчёта/коллекции, а также удаление повторов одной главы, как в интерфейсе. Области изолированы: автоматический fallback не маскирует локальную неудачу.
- На главной странице до раскрытия видны три результата, поэтому основной пользовательский показатель здесь — **Hit@3**, дополнительно Hit@1/5, MRR@10, nDCG@10 и Recall@10. Метрики считаются по главам, карточка всей записи не засчитывается как найденный ответ.

Корпус и вопросы хешируются; версии нейросетей зафиксированы. Смешивание старого нейросетевого результата с новым корпусом блокируется. Первые семь вариантов заданы до просмотра holdout-результатов. Восьмой, `current-query-clean-exploratory`, добавлен после обнаружения проблемы вопросительных слов: это **последующий исследовательский эксперимент**, не независимое подтверждение на holdout.

Это интервал для синтетического набора, не прогноз пользовательского трафика; сравнение нескольких методов и выбор лучшего добавляют оптимизм.

## Что не покрывал прежний тест

Прежние 24 вопроса были близки к формулировкам тезисов и уже использовались при исправлении поиска. На них current показывает 22/24 в топ-5 архива, на новых — 14/24. Новая оценка также убирает повторы глав и использует реальный лимит архива; поэтому разные протоколы нельзя механически смешивать.

Ручные переформулировки оказались существенно сложнее. На шести development-переформулировках current не находит ожидаемую главу в топ-3 ни разу; reranker находит в трёх случаях. На шести holdout-переформулировках current и reranker дают по 3/6, E5 — 1/6. Даже выигравший метод не решает поиск по свободно описанному намерению надёжно.

Опечатки иногда **улучшают** выдачу current: на новых вопросах топ-3 становится 13/24 вместо 12/24. Это не преимущество опечаток, а признак неустойчивости переключения exact/prefix/correction/semantic и весов отдельных слов.

## Диагноз текущей реализации

1. **«Semantic» сейчас не означает векторную семантику.** Это OR-поиск, нечёткие совпадения и ручные группы связанных слов. Название `semantic` в коде/интерфейсе не подтверждает понимание вопроса.
2. **Вопросительные слова участвуют в ранжировании.** В stop-list отсутствуют «почему», «зачем», «сколько», «чем». На вопрос о большом окне контекста среди первых кандидатов возникала глава о большом профиците калорий. Но простое вырезание этих слов не улучшило Hit@3 holdout и ухудшило Hit@5 на один вопрос: править нужно вместе с логикой выбора ветки и весами.
3. **Контекст записи не передаётся большинству глав и тезисов как отдельное поле.** «Подходы и повторения» теряют уточнение «детям». Индекс целых глав с названием записи выглядит полезной дешёвой базой, но это изменение единицы индексации плюс ранжирования, а не чистая замена одного коэффициента.
4. **Жёсткое завершение на первой найденной ветке.** Слабый exact в заголовке/карточке может закрыть доступ к более полезному частичному ответу. Предыдущее исправление решает только случай, когда exact-выдача состоит из одних карточек.
5. **Слишком широкое ручное расширение.** Совпадение одного слова из многословного понятия активирует всю группу; например «работа» связывается с работой ног/клинком. Это может добавлять фехтовальные результаты к вопросу о программировании. Изменение словаря требует отдельного измерения, здесь оно не внедрено.
6. **Символы и короткие числа теряют различия.** Токенизация превращает `pass@k` и `pass^k` в одинаковые основные токены, однозначные числа отбрасываются по длине. Для метрик, дозировок, названий и идентификаторов нужен отдельный точный сигнал.
7. **Два шарда имеют независимую BM25-статистику.** Их сырые scores объединяются, хотя корпусные частоты различаются. Это гипотеза о смещении рангов, не измеренный отдельный эффект. Возможные проверки: общий статистический корпус или fusion по рангам.
8. **Сниппет может не объяснять совпадение.** Индексируется всё transcript-окно, сохраняются первые 400 символов. Найденная фраза может находиться дальше обрезки. Нужны ленивое получение исходного окна и построение цитаты вокруг совпадения.
9. **UI и области влияют на успех.** Топ-4 скрыт на главной; поиск из отчёта может расшириться до архива ради карточки того же отчёта. Эти наблюдения первого браузерного прогона остаются актуальными; нейросетевые эксперименты проверены локальным harness, не представлены как тест готового мобильного интерфейса.

## Сопоставление с существующими решениями

| Подход | Что уже есть / чего нет | Вывод для проекта |
|---|---|---|
| MiniSearch, BM25+, поля, stemming, fuzzy | Уже есть движок, русский stemmer, префиксы, опечатки, фильтры. Нет проверенного контекста глав и общего ранжирования | Самый дешёвый путь улучшить текущий статичный сайт. Не начинать с замены библиотеки |
| Contextual retrieval | Названия и summaries есть, но не всегда доступны отдельному фрагменту при поиске | Здесь испытано добавление названия записи, **не** LLM-генерация контекста для каждого фрагмента |
| Dense retrieval | В текущем сайте нет; E5 локально испытан | На новых вопросах выигрыш существенный, но остаются лексические провалы и запросы без ответа |
| Hybrid + RRF | В текущем сайте нет; испытан k=60, до 100 кандидатов каждой системы | Устойчивый способ смешивать разные шкалы, но качество проверять: здесь он не всегда лучше dense |
| Cross-encoder reranker | В текущем сайте нет; локально испытана Jina multilingual | Самый сильный из испытанных вариантов; дополнительные задержка и вес модели |
| Pagefind | Не используется | Альтернатива для статичного сайта с небольшими загрузками по запросу. Сначала проверить русский поиск, таймкоды и главную единицу результата; здесь не разворачивался |
| Typesense / Meilisearch | Не используются | Готовые фильтры, typo tolerance и hybrid API, но требуют поискового сервиса. Их миграционная стоимость не оправдана только размером этого корпуса |
| Elasticsearch | Не используется | Удобен для сложных retrieval-pipeline и оценки ранжирования, но для 2 572 глав слишком большой первый шаг |
| SPLADE, ColBERT, BGE-M3, query rewriting / HyDE | Не испытаны в этом прогоне | Следующая серия при необходимости; нельзя объявлять их лучше измеренного варианта без русского теста, проверки памяти и задержки |

Первичные источники:

- [MiniSearch](https://lucaong.github.io/minisearch/) описывает локальный поиск, веса полей, stemming и fuzzy как строительные блоки. BM25+ и параметры дополнительно проверены в установленном `node_modules/minisearch/src/MiniSearch.ts`.
- [BEIR](https://arxiv.org/abs/2104.08663) показывает, почему важны разные домены и почему сильная лексическая база остаётся обязательной при сравнении нейросетей.
- [Contextual Retrieval, Anthropic](https://www.anthropic.com/engineering/contextual-retrieval) рассматривает потерю контекста при разбиении текста и добавление пояснения к каждому фрагменту. Проценты из их эксперимента не перенесены на наш архив.
- [RRF, Elastic](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) задаёт объединение по рангам без смешивания несовместимых сырых scores.
- [Retrieve & Re-Rank, Sentence Transformers](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) описывает двухэтапную схему: сначала кандидаты, затем совместная оценка вопроса и документа.
- [InformationRetrievalEvaluator](https://sbert.net/docs/package_reference/sentence_transformer/evaluation.html) описывает MRR, nDCG, accuracy/hit и recall для оценки retrieval.
- [Multilingual E5-small](https://huggingface.co/intfloat/multilingual-e5-small) задаёт обязательные `query:`/`passage:` префиксы, pooling с attention mask и нормализацию; всё это соблюдено.
- [Jina reranker v2 multilingual](https://huggingface.co/jinaai/jina-reranker-v2-base-multilingual) — использованная модель для пар вопрос/глава. Карточка указывает CC-BY-NC-4.0 для research/evaluation; коммерческое внедрение требует отдельного решения по модели/условиям.
- [Pagefind](https://pagefind.app/), [Typesense Vector Search](https://typesense.org/docs/28.0/api/vector-search.html), [Meilisearch hybrid modes](https://www.meilisearch.com/docs/capabilities/hybrid_search/advanced/semantic_vs_hybrid) — первичные описания альтернатив. Они изучены по документации, не сравнены здесь как установленные серверы.

## Отсутствие ответа и уверенность

На шести отрицательных запросах current возвращает совпадения в 5/6 случаях, dense и hybrid — в 6/6. Например, вопрос о квантовой телепортации может пересекаться со спортивной метафорой «телепортация». Это тематическая близость, не ответ.

У E5 даже бессмыслица получила top similarity около **0.812**. Эти значения нельзя показывать как «81% уверенности». Reranker лучше разделяет такие примеры, но его score тоже не калиброванная вероятность.

Исследовательская проверка порога raw-logit reranker:

| Порог | Отрицательные запросы с выдачей | Holdout: сохранилось успешных топ-3 |
|---|---:|---:|
| Без порога | 6/6 | 21/24 |
| −2 | 1/6 | 21/24 |
| −1 | 0/6 | 20/24 |
| 0 | 0/6 | 13/24 |

Порог −1 убирает все шесть отрицательных примеров, но теряет полезный ответ. Это **не готовая настройка**: негативов слишком мало, отдельного calibration/test-разделения для них пока нет. Лучше различать «нашли ответ» и «есть связанные материалы», а порог проверять на большем наборе настоящих запросов без ответа.

## Скорость и стоимость архитектуры

На этом Windows-компьютере, ONNX CPU, четыре потока, без сервера и сетевой передачи корпуса:

- Первый прогон кодирования 2 572 глав: около **22 секунд**. Кодирование выполнено с максимумом 512 токенов; длинные главы могут обрезаться.
- Матрица векторов: **3.95 MB** float32. При таком объёме точный перебор скалярных произведений достаточно прост; отдельная vector database/ANN не требуется для лаборатории.
- Модели: около **118 MB E5 + 280 MB reranker**, плюс tokenizer-файлы. Размеры не подходят для безусловной загрузки всего набора при первом открытии мобильной страницы.
- Изолированный прогретый векторный запрос: медиана около **5 ms** на 12 выбранных запросах; включает кодирование вопроса, точное сравнение с векторами и RRF, исключает лексический retrieval.
- Повторное ранжирование 20 кандидатов: медиана около **595 ms**, полный измеренный neural-путь — **600 ms**, p95 около **765 ms**.
- Current в Node: медиана около **183 ms**, p95 **418 ms** на архивных формулировках. Загрузка/десериализация двух готовых шардов из памяти — около **3.1 s**, без сети.
- Лексический индекс глав: около **1.38 MB**, с названием записи **1.48 MB**; прогретый поиск — меньше миллисекунды в Node. Это не прямой выигрыш «в 500 раз»: индекс содержит главы, а current также индексирует transcript-окна, материалы и отдельные тезисы.

Это desktop-измерения, не WebAssembly, не физический телефон и не браузерный end-to-end SLA. Нейросетевые timings в общих rows исключают часть стадий; для задержки использовать отдельный [single-query benchmark](lab-2026-09-06/latency-neural.json), а не время повторного прогона из кеша.

## Какие тесты теперь есть

1. **Source-grounded retrieval:** ожидаемые главы и цитаты проверяются по файлам, все 330 сценариев сохраняются, неудачи не вырезаются из метрик.
2. **Отложенный набор:** восемь новых записей отделены от шести старых, варианты одной формулировки не считаются независимыми наблюдениями в bootstrap.
3. **Perturbation:** 48 искусственных опечаток и 12 ручных переформулировок. Это не симуляция всех настоящих ошибок ввода, ASR или русской раскладки.
4. **Negative / abstention:** шесть запросов вне ожидаемого содержания, отдельный анализ порогов.
5. **Ablation:** цельная глава, название записи, доля совпавших слов, dense, RRF, reranker, последующая очистка вопросительных слов. Изолированы не все переменные: главы против полного индекса меняют и покрытие.
6. **Fault injection:** задержка transcript-шарда, HTTP 404/503, повтор после ошибки core, отсутствие карты названий. Семь новых быстрых тестов также проверяют регистр, ё/е, пробелы и жёсткие области.
7. **Проверка измерителя:** повторы не раздувают nDCG, топ-4 отличается от топ-3, raw score не влияет на RRF. Ещё четыре быстрых теста.
8. **Pooled review:** 17 оценок 0/1/2 для небольшой выборки конфликтующих результатов, с цитатами из глав. Это один и тот же assistant-reviewer, не независимая оценка двух людей; исходные holdout-метрики этим пересмотром не заменены. [Разметка](../../scripts/search-lab/pooled-judgments.json), [расхождения](lab-2026-09-06/disagreements.json).
9. **Performance:** раздельно холодная десериализация, прогретый lexical, кодирование вопроса и rerank. Не смешиваются время построения индекса и время ответа пользователю.

## Что делать дальше

**Для текущего статичного сайта:** экспериментировать с двухуровневым поиском: компактный индекс цельных глав с контекстом записи для первых ответов, затем точные transcript-фрагменты и материалы для углубления. Сохранить точные слова, числа, фильтры и таймкоды. Убрать расширение до архива ради карточки той же записи и проверить пять видимых результатов. Работу индекса вынести в Worker, чтобы тяжёлый запрос не блокировал интерфейс.

**Для заметного роста качества вопросов:** отдельный экспериментальный режим E5 + кандидаты lexical + reranker. Сначала проверить, где достаточно чистого dense, где hybrid улучшает опечатки, и сколько кандидатов действительно нужно reranker. Обслуживание модели на сервере позволит не загружать сотни мегабайт каждому посетителю; browser-only вариант требует отдельного измерения загрузки и памяти. Не нужен переход на тяжёлую поисковую БД только ради 2 572 векторов.

**До выбора production-варианта:** увеличить holdout и негативы, добавить transcript-only вопросы, уточнить все релевантные альтернативы, сделать слепую парную оценку человеком и собрать небольшую добровольную выборку реальных запросов. ## Воспроизведение

Из `video-wisper-web`:

```powershell
# Все быстрые проверки и прежний корпусный регрессионный набор:
npm test
npm run check

# Сравнение лексических вариантов; артефакты в .codex/search-lab:
npm run test:search-lab

# Опционально Python с numpy/onnxruntime/tokenizers из requirements.txt:
# Зависимости уже присутствовали в системном Python этой машины.
npm run test:search-lab -- --neural

# Отдельно время одного прогретого нейросетевого запроса:
python scripts/search-lab/benchmark.py
```

Для другого Python указать `SEARCH_LAB_PYTHON`. Для отдельного каталога эксперимента — `SEARCH_LAB_DIR`; single-query benchmark пока использует стандартный `.codex/search-lab`. Нейросетевой запуск скачивает только модели с фиксированных Hugging Face revisions, inference выполняется локально. `trust_remote_code` не используется. Модели, векторы и полные выдачи остаются в игнорируемом `.codex/search-lab`; в docs сохранены компактные результаты и методика.

Прежний [пилот](README.md) и его цифры сохранены как история отдельного протокола.
