# Проверка ранжирования глав

Продолжение фехтовального пилота. Обогащения и 32 семейства вопросов не меняются при настройке. Сравниваются четыре заранее заданных конфигурации:

| Вариант | Документ главы | Покрытие запроса при поиске похожих фрагментов |
|---|---|---|
| baseline | Заголовок + summary | Заголовок и исходный сниппет |
| chapters | Заголовок + summary + все theses | Заголовок и исходный сниппет |
| coverage | Заголовок + summary | Исходные индексированные слова + контекст и вопросы |
| combined | Заголовок + summary + все theses | Исходные индексированные слова + контекст и вопросы |

Это объединение конспекта главы, а не полный перенос транскрипта в один документ. Отдельные тезисы, окна расшифровки и материалы сохранены, чтобы не нарушить фильтры зон и поиск подробностей. Сниппет остаётся исходным; сгенерированные вопросы не показываются как цитаты. Слова новых полей влияют только на покрытие при `semantic`, а точный поиск не получает бонуса от синтетических формулировок.

`signalTerms` содержит уникальные нормализованные основы слов индексированных полей главы. Совпадения считаются с исходными основами слов запроса, не с расширенными синонимами и не с исправленными fuzzy-термами. Это позволяет отдельно проверить гипотезу о потере поисковых сигналов при оценке по короткому сниппету.

Сравнение использует 228 парных сценариев: запись, все связанные публичные коллекции, архив и 20 отрицательных проверок. Для baseline выполнены также каталог и UI-цепочки расширения — всего 436; в сравнительную сводку входят только одинаковые сценарии. Полный прогон повторяется для выбранной конфигурации. Изолированный NoName не расширяется на архив. Сводка содержит Hit@3, Hit@5, MRR@10, ложные совпадения и индивидуальные потери Hit@5 относительно baseline. Бинарная разметка известных глав неполна и не заменяет независимую человеческую оценку.

## Результат основного набора

В ячейках — попадания нужной главы в первые три / пять результатов после удаления повторов глав, как в UI.

| Вариант | Запись, 64 | Коллекции, 80 | Архив, 64 | Размер core JSON |
|---|---|---|---|---|
| baseline | 50 / 56 | 47 / 50 | 27 / 34 | 7.12 MiB |
| chapters | 56 / 58 | 55 / 60 | 28 / 34 | 7.64 MiB |
| coverage | 52 / 56 | 47 / 54 | 31 / 34 | 7.69 MiB |
| combined | 58 / 58 | 59 / 62 | 35 / 38 | 8.88 MiB |

Ни один вариант не потерял прежнее попадание Hit@5 на этом наборе. `combined` выбран для дальнейшей проверки. Основной индекс вырос примерно на 25%; отдельный индекс расшифровок остался 13.48 MiB. Это несжатый JSON, не объём сетевой передачи. В отрицательных проверках улучшения нет: по три из четырёх запросов продолжают давать посторонние совпадения в каждой проверяемой области. Это отдельная нерешённая задача оценки достаточности совпадения.

Для длинных вопросов убран неиспользовавшийся вычислительный проход fuzzy AND. На 436 сценариях baseline порядок результатов, тип совпадения и область поиска совпали с предыдущим прогоном. Тайминги сохраняются в рабочих JSON, но сильно зависят от нагрузки; доказанного ускорения браузера или мобильного устройства этот эксперимент не устанавливает.

Отдельный набор `scripts/search-enrichment/ranking-holdout.json` содержит восемь новых вопросов по сабле и мечу с баклером, составленных после фиксации конфигураций и до чтения их результатов. Они не использовались для подготовки обогащений. Проверяются исходные вопросы и опечатки. Автор тот же, поэтому набор новый, но не независимый human gold.

## Повторение

### Решение после новых вопросов

**По умолчанию остаётся baseline.** `combined` доступен через оба флага `=1`, но не включён глобально из-за выявленной индивидуальной регрессии.

| Новый набор, 16 формулировок | baseline Hit@3 / Hit@5 | combined Hit@3 / Hit@5 |
|---|---|---|
| Запись | 11 / 11 | 12 / 12 |
| Коллекции | 8 / 9 | 10 / 11 |
| Архив | 8 / 8 | 7 / 8 |

Вопрос «После батмана соперник прикрывает руку. Как обойти эту защиту для укола?» и его версия с опечаткой потеряли нужную главу в топ-5 архива: место 1 → 7. Общее число попаданий в топ-5 это скрывает, потому что другие вопросы улучшились. Поэтому индивидуальные потери проверяются отдельно. Эти восемь вопросов теперь раскрыты и не могут повторно считаться новым контрольным набором при дальнейшей настройке.

Следующий эксперимент должен проверить причину конкуренции глав в архиве и ограничение бонуса от большого объединённого документа. Настройки нужно выбирать на уже раскрытых вопросах, а подтверждать на другом, заранее отложенном наборе. Расширять обогащение на весь архив до этого не следует.

Полный повтор `combined` на основном наборе (`FENCING_SEARCH=selected-ranking`) завершён: 436 парных сценариев, без потерь Hit@5 относительно baseline; проверки принадлежности результатов области прошли. Это подтверждает корректность цепочек расширения на основном наборе, но не отменяет регрессию на новых вопросах.

Финальная проверка обычной конфигурации: `npm test` — 43 passed, два экспериментальных теста штатно пропущены; `npm run check` — 0 ошибок и предупреждений; `npm run build` — успешно. После перезапуска preview на 4176 запрос про упражнение против реакции на каждое движение соперника показал главу «Проблема учеников и „Око“» третьей в коллекции Овчинникова, с исходным фрагментом и ссылкой на время. Ошибок браузера не обнаружено. Публикация не выполнялась.

### Команды

```powershell
npm run test:search-ranking
```

Команда последовательно пересобирает индекс для четырёх вариантов. После успеха или ошибки восстанавливается индекс с обычными настройками. Исходные отчёты и sidecar не меняются. Полные выдачи находятся в `.codex/search-fencing/ranking-*.json`, сводка — [ranking.json](ranking.json).

Для проверки выбранных вариантов на новых вопросах:

```powershell
$env:FENCING_FIXTURE = 'scripts/search-enrichment/ranking-holdout.json'
$env:SEARCH_RANK_VARIANTS = 'baseline,chapters,coverage,combined'
npm run test:search-ranking
Remove-Item Env:FENCING_FIXTURE
Remove-Item Env:SEARCH_RANK_VARIANTS
```

В `SEARCH_RANK_VARIANTS` оставить baseline и проверяемый вариант. Сводка нового набора сохраняется отдельно в `ranking-holdout.json`. Явные `SEARCH_CHAPTER_BODY=0/1` и `SEARCH_SIGNAL_TERMS=0/1` задают настройки сборщика для отката и сравнения; модель при сборке или запросах не запускается.
